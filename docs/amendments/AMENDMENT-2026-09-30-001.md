## Motivo
Docs 02/08 definem User/Workspace/WorkspaceMember e exigem autorização server-side, mas nenhum documento define o mecanismo de autenticação da V1 (login local? chave de API? single-user?). A implementação atual expõe a API local (127.0.0.1) sem authN, com scoping explícito por workspace_id.

## Documento afetado
Documento 02 (Entities), Documento 08 (Profile/Workspace Authorization)

## Regra anterior
Não especificado — lacuna.

## Nova regra
V1 local-first: autenticação desativada; API vinculada a 127.0.0.1; toda chamada declara workspace_id/profile_id validado server-side contra o banco. AuthN real (login + sessão) entra na V2 com multiusuário.

## Impacto de produto
V1 monousuário local; sem impacto no produto final multiusuário.

## Impacto arquitetural
Endpoints atuais recebem workspace_id explícito; a camada de authN será um middleware na V2 sem mudar contratos de negócio.

## Impacto de segurança
Aceitável apenas porque a API escuta em loopback. Se exposta em rede, authN torna-se OBRIGATÓRIO antes.

## Impacto de dados
Nenhum — users/workspace_members já existem nas tabelas.

## Impacto de compatibilidade
Endpoints ganharão identity na V2; clientes locais precisarão ajustar.

## Testes necessários
Testes de isolamento atuais (workspace mismatch → 404) já cobrem o scoping.

## Decisão
SUPERADA

## Aprovado por
Dono do projeto — decisão registrada em 2026-10-02.

> A implementação real foi além da proposta: autenticação completa (Argon2id, sessões opacas de 12h, verificação de e-mail, reset, membership, revogação) já opera na V1 web. A proposta de API sem authN ficou obsoleta — nada a desligar.
